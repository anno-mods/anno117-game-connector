Live game data → Anno 117 Calculator

Codebase Context

anno-117-pipe (this repo, C++20, Windows-only, branch mvp-calculator-bridge) reads the game's live production statistics over a Windows named pipe (\\.\pipe\anno117), client-only, and today only renders them in an ImGui/Direct3D12 window — nothing is exposed outside the process. Its AreaProductionStatistics messages carry, per area and per ProductGuid: live and theoretical-max generation/consumption rates, a building count (AmountOfBuildings), upkeep/income/profit (in-game currency), and productivity sums. The pipe reconnects automatically across game restarts. The project just adopted CMake + vcpkg (manifest mode, vendored submodule) + Visual Studio 2022, with zero dependencies declared so far — this integration is the explicit next stage.

../anno-117-calculator is a separate, real, actively-maintained community tool (TypeScript + Knockout.js, static webpack site, MIT-licensed, public releases, its own Discord and donations — not a prototype). It has no server and no existing live-data channel. Game GUIDs (the same space as this pipe's ProductGuid) are baked into its bundle by a sibling asset-extractor tool. Its writable state lives at Factory.buildings.constructed (a Knockout observable — exactly what a user types in today); a Product can have multiple factories, so the pipe's per-product aggregates don't always resolve to one factory. The only existing "data in" path dumps/restores all of localStorage via a file picker and reloads the page — unusable for a live, ticking feed.

Public web research (general Anno 117 game mechanics only — neither project repo was searched) confirmed the in-game Statistics screen already plots production/consumption as rates over time, matching this pipe's field shapes, and that the game's buff/attribute system is the same one the calculator already models.

Topic Axes

  • 1. Transport / IPC mechanism — how the pipe-reading process and the calculator's webview/browser talk to each other
  • 2. Process & packaging topology — one bundled app vs. two cooperating processes vs. browser extension vs. headless service
  • 3. Data-model mapping & write semantics — resolving product-level pipe aggregates onto per-factory calculator state; read-only overlay vs. direct write; the multi-factory-per-product ambiguity
  • 4. Distribution & update lifecycle — how a native companion interacts with the calculator's existing static-site/GitHub-release distribution and its real user base
  • 5. Trust, safety & non-invasiveness — this is explicitly an unofficial/experimental game feature; local-only, no elevated privileges, no resemblance to memory-injection/cheat tooling

On the user's own idea (Tauri bundle + serving .exe)

Evaluated, not rejected. Four independent ideation frames converged on a lighter variant of the same instinct: skip Tauri's Rust/webview toolchain and have the existing C++ app serve the calculator's already-built static files plus a live data feed from one small embedded HTTP server (survivor #1). That gets the same "one exe to double-click" outcome the Tauri idea is reaching for, without adding a second language/build toolchain to a project that just deliberately started clean with CMake + vcpkg and zero dependencies. Tauri remains a legitimate later choice — e.g. as a nicer packaging/UI shell wrapped around the same local-server core — but isn't necessary to reach the goal for v1.

Ranked Ideas

  • 1. Local server, no Tauri
  • 2. Read-only first, never auto-write
  • 3. GUID-blind native layer
  • 4. Versioned wire contract
  • 5. Loopback + consent by default
  • 6. Ship a non-live snapshot MVP first
  • 7. Independent product identity
1

Local server embedded in the existing C++ app — no Tauri required

Axis 2 · Process & packaging topology Confidence: High Complexity: Medium
Description
The pipe-reading exe grows a tiny embedded HTTP server (e.g. cpp-httplib) that serves the calculator's own already-built dist/ output on http://localhost:PORT and pushes live snapshots alongside it (SSE or WebSocket, same-origin). One process, one download, zero new language/toolchain — the project is already C++/CMake/vcpkg. The calculator itself needs no code changes to keep working for everyone who never runs the companion; it's purely additive.
Basis
direct: the calculator is "a static, webpack-bundled site (npm run build -> dist/). No server, no IPC" and is MIT-licensed — a static folder is trivially servable. vcpkg.json "currently has zero dependencies," so this is the cheapest moment to pick the serving model before anything else is built against a different assumption. reasoned: serving same-origin over plain http://localhost also sidesteps the mixed-content/wss problems a ws://localhost connection from the real https://anno-mods.github.io deployment would hit.
Rationale
This idea converged independently across four of the five ideation frames (leverage, cross-domain analogy, and both assumption-breaking/constraint-flipping passes) — the strongest agreement signal in the whole run. It directly answers the Tauri question with a lighter equivalent that reuses tooling already in place.
Downsides
Still a new native dependency (an HTTP library) and a listening socket, which can trigger a first-run Windows Firewall prompt — mitigate via loopback-only binding (survivor #5). A leaner fallback exists if a server proves too heavy: write snapshots to a file and poll/read them (no socket at all), at the cost of higher latency and, for browser-side reads, a repeated file-access permission grant.
Confidence
High — 4 of 5 independent ideation frames reached a form of this idea without prompting each other.
Complexity
Medium — one new vcpkg dependency, a small HTTP/SSE server, and static-file serving; no new language or build system.
2

Read-only comparison overlay first — never auto-write to buildings.constructed

Axis 3 · Data-model mapping & write semantics Confidence: High Complexity: Low
Description
Resolve pipe fields into a visually distinct, read-only "ghost" overlay next to the calculator's existing numbers — comparing the pipe's live ProductGeneration/ProductConsumption against the calculator's own totalCurrentProduction/totalDemand computed values. Never call factory.buildings.constructed(n) automatically. Editing stays 100% manual.
Basis
direct: Factory.buildings.constructed is "exactly what a user types into the UI today" — a planning input, not a current-state field — and "a product can be produced by more than one factory type/tier, so the pipe's per-product aggregate... doesn't always map 1:1 to a single calculator Factory object." reasoned: a planning tool's value is exploring hypotheticals different from current reality; auto-writing collapses "what I have" and "what I'm planning" into one field, silently overwriting a user's scenario the next time the pipe ticks.
Rationale
This is the single strongest convergence in the entire run — a version of it was independently proposed by all five ideation frames. It also removes the hardest unsolved problem (multi-factory disambiguation) from the critical path entirely, since Product-level computed values are already summed across every factory tier and need no per-factory resolution.
Downsides
Users who specifically want "auto-sync my building counts" don't get it in v1; that has to be a deliberate, later, opt-in feature (see the algebraic-solve fallback in the rejection summary) if ever built at all.
Confidence
High — unanimous across every ideation frame; treat as close to a settled constraint rather than a debatable option.
Complexity
Low — it's a scope decision more than an engineering task, and it's the cheapest possible choice to make explicitly now versus discovering the problem after shipping writes.
3

Keep the native layer GUID-blind — all mapping logic lives in the calculator's own TypeScript

Axis 3 · Data-model mapping & write semantics Confidence: High Complexity: Low–Medium
Description
The C++ side never resolves ProductGuid to a Factory or reasons about the game's asset graph at all — it forwards ProductionEntryData fields verbatim. All GUID → Asset → Product → Factory resolution reuses the calculator's own assetsMap, which asset-extractor already bakes into js/params.js at build time.
Basis
direct: "Game asset data is baked into js/params.js at build time by a separate sibling tool (../asset-extractor) — shares the same numeric GUID space as this pipe's ProductGuid," and "Per-island assetsMap: Map<guid, Asset> holds Factories/Products/Buffs etc., keyed by the game's own GUIDs."
Rationale
Removes an entire category of future bugs (a hand-maintained GUID table drifting out of sync across two languages and two repos as the game updates) by not building one at all — the mapping is already generated, for free, every time asset-extractor runs. It also keeps the native binary's contract stable (see survivor #4), since it never has to be rebuilt when the calculator's domain model changes.
Downsides
Means the native side can't do anything "smart" with the data on its own (e.g. its own ImGui overlay would also need the mapping if it ever wanted factory-level detail) — an acceptable trade given the ImGui viewer's job is graphing raw trends, not domain reasoning.
Confidence
High — proposed independently by two frames and directly supported by the existing asset-extractor/GUID-sharing pattern already in place between the two repos.
Complexity
Low–Medium — mostly a discipline/scope constraint on the native side; the actual mapping code is new work regardless of where it lives.
4

Explicit versioned wire contract, decoupled from both repos' release cadences

Axis 4 · Distribution & update lifecycle Confidence: High Complexity: Low
Description
Define the bridge's JSON payload as a small, explicit, versioned schema with a capability/version handshake on connect (mirroring the pipe protocol's own existing Version message pattern one layer down). A version mismatch degrades gracefully ("live features disabled") instead of breaking silently.
Basis
direct: the pipe protocol already has a dedicated Version message type as one of its four message kinds — the project has already solved "how do two independently-evolving processes agree on protocol shape" once, for the game↔bridge link. reasoned: the calculator deploys continuously as a static site on its own cadence, entirely outside this repo's control, while the native binary updates far less often (a download, potentially SmartScreen-flagged) — without negotiation, any calculator deploy risks silently breaking against whatever bridge version a user still has installed.
Rationale
Converged across three independent frames, including two different cross-domain analogies (SimConnect's variable registry, Stream Deck's independently-versioned plugin protocol) that both land on the same shape: two systems on different release schedules need an explicit contract, not an assumed one.
Downsides
A small amount of schema/versioning ceremony up front for a project that currently has none — worth it here because retrofitting version negotiation after users already depend on an implicit contract is much more expensive.
Confidence
High — three frames converged, and the pattern already exists one layer down in this same protocol.
Complexity
Low — a version field plus a capability check; cheap now, expensive to add later.
5

Loopback-only, explicit opt-in connection — treat trust as a first-class design decision

Axis 5 · Trust, safety & non-invasiveness Confidence: High Complexity: Low
Description
Bind the local server strictly to 127.0.0.1, require an explicit user action in the calculator ("Connect to running game" — not silent auto-attach on page load) before any connection opens, and stop the moment the tab/connection closes. No auto-start-on-boot, no always-on background daemon.
Basis
direct: the README already "calls the pipe an unofficial/experimental 'easter egg' feature, 'not an official or supported API'" and the pipe app is "client-only (never writes back to the game)." reasoned: a companion tool that opens a discoverable network port with no explicit consent step is one antivirus/Windows-Defender heuristic away from resembling the memory-injection/cheat-tool category this project explicitly wants no association with; an always-on background process reading a private game pipe reads very differently, trust-wise, than a tool the user explicitly invokes per session.
Rationale
Four frames converged on some version of this (loopback+ephemeral port+pairing token, an explicit consent handshake analogous to Discord RPC, an OS-level provably-read-only pipe handle, and an explicit user-initiated "Connect" action) — all pointing at the same underlying decision: default to the narrow, visible, user-initiated version of this feature, not the wide, silent one.
Downsides
Slightly more friction per session than "it just works automatically" — an acceptable, and probably necessary, cost for a tool this close to the trust-sensitive edge of game modding/tooling.
Confidence
High — four frames converged on the same underlying principle from different angles.
Complexity
Low — almost entirely default/configuration choices, not new engineering.
6

Ship a non-live, post-session snapshot MVP before building real-time streaming

Axis 3 · Data-model mapping & write semantics Confidence: Medium Complexity: Low
Description
Challenge the assumption that data must flow while the game is running. For v1, have the pipe app periodically write a small JSON snapshot (session stats, not full localStorage) to disk; extend the calculator's existing file-picker import flow to merge that snapshot into the relevant per-island observables without the current full location.reload(). Playing and analyzing become sequential, not simultaneous — no live channel, no server, needed at all for this scope.
Basis
direct: the calculator's only existing "get data in" path today — installImportConfigListener()/exportConfig() — is exactly this shape (file in, merge, minus the full-reload problem), and the grounding explicitly notes that mechanism is "not remotely suited to a live, ticking data feed... a reload per pipe update would nuke UI state" — a critique that applies only if the goal is live, not to a deliberate one-time post-session import.
Rationale
This is the one idea in the survivor set that reduces scope rather than architecture — it directly interrogates "live" as an assumption the user's framing carried in by default, and offers a legitimately much cheaper de-risking step: prove the GUID mapping and the overlay UX work at all, before building any transport, discovery, or trust-boundary machinery.
Downsides
Doesn't deliver the "watch it update while I play" experience the user is presumably actually after — it's a deliberate v1/v2 split, not a replacement for survivors #1, #4, #5 if live data is the real goal.
Confidence
Medium — grounded in existing code (the import mechanism genuinely supports this shape) but it's a scope call, not a technical necessity, so its value depends on how much the team actually wants "live" for v1.
Complexity
Low — reuses an existing mechanism almost as-is.
7

Ship the companion as its own independently-versioned product, never gating the calculator's release

Axis 4 · Distribution & update lifecycle Confidence: Medium Complexity: Low
Description
Publish the native companion from this repo's own releases, named and versioned independently (e.g. "Anno 117 Live Data Bridge"), explicitly for the subset of users who also want live stats — never bundled into or required by the calculator's mainline distribution.
Basis
direct: the calculator is "a real, actively maintained community tool by the same author with a Discord and PayPal donations" — a real reputation and userbase to protect — and the two repos are already organizationally separate, with this repo already standing up its own independent build (CMake + vcpkg). reasoned: an unsigned, niche companion exe (see the SmartScreen "unrecognized publisher" friction any new native binary hits) is exactly the kind of release risk that should not ride on the calculator's existing reputation with its real user base.
Rationale
Keeps the calculator's frictionless "just open a URL" path completely untouched for the ~majority of users who never want live data, while still giving the feature a real, discoverable home. Also sets up a clean path to "support other Anno calculators or mods" later, since the bridge isn't calculator-specific by construction.
Downsides
Two release processes to maintain instead of one; discoverability of the companion depends on the calculator surfacing it (a link, a settings-panel mention) rather than it being bundled by default.
Confidence
Medium — directionally well-supported, but the actual distribution mechanics (where the download link lives, how discovery works) weren't scoped by this ideation pass.
Complexity
Low — primarily a naming/repo-layout/release-process decision, not new code.
